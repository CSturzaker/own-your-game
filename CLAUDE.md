## What this is

**Own Your Game** is a UNICEF youth-led campaign site anchored on the 2026
FIFA World Cup. Around 350 young people (~42 countries, ages 11–18) record
30–60s videos on what sport means to them, signing an open letter to FIFA.
One sentence: *350 young people are writing a letter to FIFA. Meet the team.*

Multilingual, mobile-first, low-bandwidth. Donor lands → understands the
campaign in five seconds. Young person lands → wants to tap a face.

**Anchor date:** 2026 FIFA World Cup. Project target date: 2026-06-05.

## Tech stack (locked)

- **Framework:** Astro 4+ (latest stable) with React 18 islands
- **Language:** TypeScript, `strict: true`, `noUncheckedIndexedAccess: true`
- **Styling:** Tailwind CSS, configured to consume design tokens as CSS
  custom properties via `theme.extend`
- **Interactive primitives:** Radix UI (`@radix-ui/react-*`) only — never a
  styled component library
- **Validation:** Zod
- **Testing:** Vitest + React Testing Library (unit); Playwright +
  `@axe-core/playwright` (e2e + a11y); Lighthouse CI (perf budgets)
- **Tooling:** pnpm, Node 22 LTS, ESLint, Prettier, Husky + lint-staged,
  commitlint
- **Hosting:** Cloudflare Pages, Cloudflare Stream (video), Cloudflare R2
  (portraits) — **not provisioned yet**

These are locked decisions. Don't drift. Don't add dependencies "while
you're here" — justify every new dep in the PR.

## Hard rules

- **pnpm only.** No `package-lock.json`, no `yarn.lock`. Pin via
  `packageManager` in `package.json` and `.nvmrc` for Node 22.
- **TypeScript strict from day one** including `noUncheckedIndexedAccess`.
  Don't relax it.
- **No Cloudflare credentials yet.** Agency hasn't created the account.
  Anything needing real CF creds is blocked.
- **No secrets in the repo.** Only `.env.example` with placeholder names.
- **Safeguarding (permanent, non-negotiable):**
  - First names only in public UI. Schema must not allow surnames.
  - No public submission form. No comments. No DMs. No accounts.
  - Video comments disabled at the Cloudflare Stream level.
  - Portrait images are static stills supplied separately; no upload path.
  If a future issue asks for something that violates these, refuse and flag
  it on the issue.
- **Design tokens only.** No ad-hoc colour, spacing, or radius values that
  bypass the tokens defined in `hifi-tokens.css` / Tailwind config.
- **Performance & a11y budgets are enforced in CI:** <500KB initial home
  load on 3G, <3s TTI on simulated mid-range Android over 3G, zero
  axe-core WCAG 2.1 AA violations, no video loads until a card opens,
  reduced-motion respected globally, full keyboard navigation.

## Git: branches, commits, PRs

- **One branch per issue**, using the `gitBranchName` Linear suggests on
  each issue (e.g. `craigdsturzaker/dev-12-astro-react-ts-scaffold`).
- **One PR per issue**, targeting `main`. Squash merge.
- **PR title:** `DEV-XX: <issue title>`. PR body copies the issue's Goal and
  walks through each acceptance criterion with how it was satisfied.
  Reference the issue ID so Linear auto-links.
- **CI must be green** before merge.
- **Conventional Commits** for every commit:
  ```
  <type>(<optional scope>): <short imperative summary>

  <optional body explaining what and why, wrapped at 72 chars>

  Part of DEV-XX
  ```
  - Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `style`,
    `perf`, `ci`, `build`.
  - Imperative mood ("add", not "added"). Lowercase summary, no trailing
    period, ≤72 chars.
  - Don't put the issue ID in the summary line — only in the body via the
    `Part of DEV-XX` trailer (Linear watches for this exact phrase).
  - **No author trailers.** No `Co-authored-by`, no `Signed-off-by`, no
    "Generated with Claude Code" lines.
- **Commit grouping:** group by intent, not by file. One commit = one
  coherent change. A typical DEV-XX implementation is 3–8 commits.
- **No `wip`, no "fix typo" chase commits.** Rebase/amend them out before
  the PR. No mixed-concern commits.
- Commitlint + `commit-msg` Husky hook enforces most of this once DEV-18
  lands. Until then, follow it by hand.

## How to work an issue

1. Read the Linear issue in full (Goal, Scope, AC, Technical Notes,
   comments).
2. Re-read the project overview if it's been a while.
3. Read relevant `design/handoff/project/*.jsx` for the area.
4. Read existing code under the touched paths.
5. Plan. If the plan diverges from the issue, surface it in a PR
   description or Linear comment before implementing.
6. Implement. Stick tightly to scope — no polish from later issues.
7. Run the full local loop: `pnpm install && pnpm typecheck && pnpm lint &&
   pnpm test && pnpm build` (each available from the issue that adds it).
8. Verify every acceptance criterion. Open the PR. Stop and wait.
