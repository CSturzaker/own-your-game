# Internationalisation (i18n)

How the site routes, renders, and (eventually) translates its five
languages. This document covers the **routing layer** shipped in DEV-69.
UI-string translation (the dictionaries), RTL layout, and the language
switcher arrive in DEV-70 / DEV-71 / DEV-72 and extend the notes here.

## The five locales

| Code | Language  | Direction | URL prefix      |
| ---- | --------- | --------- | --------------- |
| `en` | English   | LTR       | _(none — root)_ |
| `es` | Español   | LTR       | `/es`           |
| `fr` | Français  | LTR       | `/fr`           |
| `ar` | العربية   | RTL       | `/ar`           |
| `pt` | Português | LTR       | `/pt`           |

The locale set is declared **once**, in `src/i18n/config.ts`
(`LOCALES`, `DEFAULT_LOCALE`, `NON_DEFAULT_LOCALES`, `RTL_LOCALES`).
`astro.config.mjs` imports `LOCALES` and `DEFAULT_LOCALE` from that file,
so the build-time routing config and the app-side helpers can never
drift. It mirrors `LETTER_LANGS` in `schemas/letter.ts`.

## Routing model

Configured in `astro.config.mjs` under `i18n`:

- `defaultLocale: "en"` — English is the launch language.
- `routing.prefixDefaultLocale: false` — English is served from the root
  with **no** prefix (`/letter`, not `/en/letter`); every other locale
  carries its prefix (`/es/letter`).

### Page structure

Each of the four pages exists as a thin route file that renders a shared
body component from `src/components/pages/`:

```
src/pages/
  index.astro            →  /            (en)   ─┐
  letter.astro           →  /letter      (en)    │ render
  squad.astro            →  /squad       (en)    ├─ <Home/> <Letter/>
  about.astro            →  /about       (en)    │   <Squad/> <About/>
  [lang]/
    index.astro          →  /:lang/      (es…)   │ (src/components/pages/*)
    letter.astro         →  /:lang/letter        │
    squad.astro          →  /:lang/squad         │
    about.astro          →  /:lang/about        ─┘
```

The `[lang]/*.astro` files use `getStaticPaths()` over
`NON_DEFAULT_LOCALES` to generate one static route per non-default
locale. The shared body components read `Astro.currentLocale` (which
Astro derives from the URL prefix) and render locale-correct content and
internal links — so there is **one** body per page, rendered at both the
English and the localised URLs.

### Why not `i18n.fallback`?

Astro's `i18n.fallback` (render the default-locale page when a localised
page is missing) **does not work in a pure static build** (`output:
"static"`, no SSR adapter). It generates competing routes that shadow
the explicit `[lang]/` pages and emit **empty files** — verified at
build time during DEV-69 (the localised pages logged `file not created,
response body was empty`). So we don't use it.

The "never 404, fall back to English" intent is met at the **content
layer** instead:

- **UI strings (DEV-70):** the translation dictionary returns the
  English value for any key not yet translated in a locale.
- **The letter:** `content/letter/{es,fr,ar,pt}.md` ship English body
  copy (stubs from DEV-33) until the campaign team translates them, so
  `/es/letter` always renders something readable.

Because every real page has an explicit `[lang]/` route, no page-level
fallback is needed. Pages that exist only in English (e.g. `/demo/*`)
simply have no localised variant — `/es/demo/...` 404s, which is correct
(the demo surfaces are dev-only and robots-excluded in DEV-81).

## Internal links: `localiseUrl`

`src/i18n/localise-url.ts` exports `localiseUrl(path, targetLocale)`,
which converts an internal path to its equivalent in another locale:

```ts
localiseUrl("/letter", "es"); // "/es/letter"
localiseUrl("/es/letter", "en"); // "/letter"   (default = no prefix)
localiseUrl("/", "ar"); // "/ar"
localiseUrl("/squad?theme=joy#x", "es"); // "/es/squad?theme=joy#x"
```

It strips any existing known prefix before applying the target, preserves
query strings and hashes, and treats an unknown target as the default
(unprefixed). The shared chrome routes its internal links through it:

- **`Wordmark.astro`** — the home link (`/` → `/es`).
- **`Header.astro`** — the primary nav.
- **`Footer.astro`** — the column links (external links and `#` stubs are
  left untouched).
- **Page CTAs** — e.g. the home hero's "Read the letter" / squad buttons.

DEV-72 reuses `localiseUrl` to drive the footer language switcher
(navigating to the current path in the chosen locale, preserving query
and hash).

## `html lang`

`BaseLayout.astro` defaults its `lang` prop to
`resolveLocale(Astro.currentLocale)`, so every page emits the correct
`<html lang="…">` automatically. RTL `dir="rtl"` for Arabic is added in
DEV-71 (the metadata is ready — `RTL_LOCALES` / `isRtl()` in
`src/i18n/config.ts`).

## Adding a new language

1. Add the code to `LOCALES` in `src/i18n/config.ts` (and to
   `RTL_LOCALES` if it reads right-to-left). `astro.config.mjs` and the
   `[lang]/` routes pick it up automatically.
2. Add the code to `LETTER_LANGS` in `schemas/letter.ts` and create
   `content/letter/{code}.md` (start from `en.md`; the campaign team
   translates it — see `letter-editing.md`).
3. Add a dictionary file under `src/i18n/dictionaries/{code}.json`
   (DEV-70) with every key present (English values or `TODO: translate`
   stubs — the CI guard enforces key parity).
4. Add the native language name to the switcher data (DEV-72).

Nothing else — routing, the switcher, and `localiseUrl` all read from
the locale list.

## Working with translators

Translators edit JSON dictionaries (`src/i18n/dictionaries/*.json`,
DEV-70) and the letter markdown (`content/letter/*.md`) directly; there
is no translation-management system in scope. The CI key-parity guard
(DEV-70) means a missing key fails the build rather than silently
shipping an English string at a Spanish URL. Until a string is
translated, the English fallback renders — safe, never broken.
