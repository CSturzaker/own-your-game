# Internationalisation (i18n)

How the site routes, renders, and (eventually) translates its five
languages. This document covers the **routing layer** shipped in DEV-69.
UI-string translation (the dictionaries), RTL layout, and the language
switcher arrive in DEV-70 / DEV-71 / DEV-72 and extend the notes here.

## The five locales

| Code | Language  | Direction | URL prefix      |
| ---- | --------- | --------- | --------------- |
| `en` | English   | LTR       | _(none — root)_ |
| `es` | Español   | LTR       | `/es`           |
| `fr` | Français  | LTR       | `/fr`           |
| `ar` | العربية   | RTL       | `/ar`           |
| `pt` | Português | LTR       | `/pt`           |

The locale set is declared **once**, in `src/i18n/config.ts`
(`LOCALES`, `DEFAULT_LOCALE`, `NON_DEFAULT_LOCALES`, `RTL_LOCALES`).
`astro.config.mjs` imports `LOCALES` and `DEFAULT_LOCALE` from that file,
so the build-time routing config and the app-side helpers can never
drift. It mirrors `LETTER_LANGS` in `schemas/letter.ts`.

## Routing model

Configured in `astro.config.mjs` under `i18n`:

- `defaultLocale: "en"` — English is the launch language.
- `routing.prefixDefaultLocale: false` — English is served from the root
  with **no** prefix (`/letter`, not `/en/letter`); every other locale
  carries its prefix (`/es/letter`).

### Page structure

Each of the four pages exists as a thin route file that renders a shared
body component from `src/components/pages/`:

```
src/pages/
  index.astro            →  /            (en)   ─┐
  letter.astro           →  /letter      (en)    │ render
  squad.astro            →  /squad       (en)    ├─ <Home/> <Letter/>
  about.astro            →  /about       (en)    │   <Squad/> <About/>
  [lang]/
    index.astro          →  /:lang/      (es…)   │ (src/components/pages/*)
    letter.astro         →  /:lang/letter        │
    squad.astro          →  /:lang/squad         │
    about.astro          →  /:lang/about        ─┘
```

The `[lang]/*.astro` files use `getStaticPaths()` over
`NON_DEFAULT_LOCALES` to generate one static route per non-default
locale. The shared body components read `Astro.currentLocale` (which
Astro derives from the URL prefix) and render locale-correct content and
internal links — so there is **one** body per page, rendered at both the
English and the localised URLs.

### Why not `i18n.fallback`?

Astro's `i18n.fallback` (render the default-locale page when a localised
page is missing) **does not work in a pure static build** (`output:
"static"`, no SSR adapter). It generates competing routes that shadow
the explicit `[lang]/` pages and emit **empty files** — verified at
build time during DEV-69 (the localised pages logged `file not created,
response body was empty`). So we don't use it.

The "never 404, fall back to English" intent is met at the **content
layer** instead:

- **UI strings (DEV-70):** the translation dictionary returns the
  English value for any key not yet translated in a locale.
- **The letter:** `content/letter/{es,fr,ar,pt}.md` ship English body
  copy (stubs from DEV-33) until the campaign team translates them, so
  `/es/letter` always renders something readable.

Because every real page has an explicit `[lang]/` route, no page-level
fallback is needed. Pages that exist only in English (e.g. `/demo/*`)
simply have no localised variant — `/es/demo/...` 404s, which is correct
(the demo surfaces are dev-only and robots-excluded in DEV-81).

## Internal links: `localiseUrl`

`src/i18n/localise-url.ts` exports `localiseUrl(path, targetLocale)`,
which converts an internal path to its equivalent in another locale:

```ts
localiseUrl("/letter", "es"); // "/es/letter"
localiseUrl("/es/letter", "en"); // "/letter"   (default = no prefix)
localiseUrl("/", "ar"); // "/ar"
localiseUrl("/squad?theme=joy#x", "es"); // "/es/squad?theme=joy#x"
```

It strips any existing known prefix before applying the target, preserves
query strings and hashes, and treats an unknown target as the default
(unprefixed). The shared chrome routes its internal links through it:

- **`Wordmark.astro`** — the home link (`/` → `/es`).
- **`Header.astro`** — the primary nav.
- **`Footer.astro`** — the column links (external links and `#` stubs are
  left untouched).
- **Page CTAs** — e.g. the home hero's "Read the letter" / squad buttons.

## Language switcher (DEV-72)

The footer language switcher (`src/islands/LanguageSwitcher.tsx`) is a
Radix Popover. The options are **buttons, not links**, because selecting
navigates programmatically: `window.location.assign(localiseUrl(path,
code))`. The path comes from `window.location` at click time (so it
carries any live query the SSR path lacks — e.g. the squad filters) and
falls back to the `Astro.url.pathname` the host passes in. Switching to
the default locale drops the prefix; the query and hash are preserved.

`Footer.astro` resolves the option list — every locale by its **native
name** from the dictionary (`languages.{code}`) — and threads it in along
with the current locale and the popover direction (the island can't call
`t()`). The trigger shows the current language's native name.

RTL alignment: Radix Popover has no direction context here, so `start`/
`end` resolve physically (left/right). The switcher and the squad filter
popovers flip `Popover.Content`'s `align` to `end` under RTL so the menu
opens from the trigger's trailing edge. (Tooltips and the Dialog wrapper
still default to LTR alignment — a minor remaining refinement; a
`DirectionProvider` would cover them but needs `@radix-ui/react-direction`
as a direct dep.)

## UI strings: the dictionary + `t()` (DEV-70)

Every user-facing UI string lives in a per-locale JSON dictionary under
`src/i18n/dictionaries/{en,es,fr,ar,pt}.json`. `en.json` is the source of
truth; the other locales mirror its key structure exactly.

### Resolving a string

- **Astro components**: `const { t, tList, locale } = makeT(Astro.currentLocale)`
  then `t("about.title")`. `tList("about.body")` returns a string array
  for repeated text blocks (the About body + closing pair).
- **`t(key, vars?)`** walks the dot-path key, falls back to English when
  the locale hasn't translated it, then substitutes `{var}` placeholders:
  `t("squad.grid.loadMore", { count: 24 })` → "Load 24 more".

### The `TODO: translate` sentinel

A non-English value of `"TODO: translate"` means "key present, not yet
translated". It satisfies the CI parity guard (so we ship complete key
sets) but **resolves to the English string at runtime** — a
half-translated locale shows English, never the marker. A key missing (or
non-string) in English too is a content bug and throws at build time.

### React islands take strings as props

`src/i18n/t.ts` statically imports all five dictionaries, so importing it
into an island would ship every translation to the browser. Islands
instead receive the resolved strings — or `{var}` templates — as props
from their Astro host, and use the pure `interpolate()` from
`~/i18n/interpolate` for any client-side count substitution. The squad
filter/grid bundles are assembled by `buildSquad*Strings` in
`src/i18n/squad-strings.ts` (shared by `Squad.astro`, the demo pages, and
the island tests). The rotation, signed-by, and letter-rail islands take
smaller bespoke `strings` props. Client-side scripts (the share section)
read their strings from `data-*` attributes the server render sets.

### Known limitations (follow-ups)

These render the **English fallback** today and are flagged for later:

- **No translations beyond the delivered set.** The campaign team
  delivered the home "starting eleven" section, the tagline, the About
  prose, and the letter prose (es/fr/ar). Everything else (nav, footer,
  squad filters, voice counter, etc.) is `TODO: translate` → English.
  Portuguese is entirely stubbed.
- **Squad desktop headline** spells the count out in words
  (`squadHeadlineDesktop`), which is English-only; other locales reuse the
  numeral form (`squad.headlineMobile`) at both breakpoints.
- **The letter `::values` motif** keeps English tokens
  (`community`/`friendship`/…) in every locale: its dot-colour map and the
  "About {word}." label in `src/lib/letter-render.ts` (DEV-53) are keyed
  on the English words. Localising the motif is a letter-renderer
  follow-up.
- **Country/language display names** come from `Intl.DisplayNames(["en"])`
  and number grouping from `formatVoiceCount` (en-US). Per-locale
  formatting is a future refinement.

## `html lang` and `dir`

`BaseLayout.astro` defaults its `lang` prop to
`resolveLocale(Astro.currentLocale)`, so every page emits the correct
`<html lang="…">` automatically, and sets `dir="rtl"` when
`isRtl(lang)` is true (`RTL_LOCALES` in `src/i18n/config.ts` — currently
`["ar"]`), `ltr` otherwise.

## RTL layout (Arabic) — DEV-71

`dir="rtl"` on `<html>` cascades to the whole tree, so most mirroring is
automatic: flex/grid containers lay their items out right-to-left (the
header nav, footer columns, and squad filter chips reverse with no code),
and Tailwind's **logical utilities** flip. The rule:

- **Use logical utilities for horizontal direction**, not physical ones:
  `ps-`/`pe-` (not `pl-`/`pr-`), `ms-`/`me-` (not `ml-`/`mr-`),
  `inset-s-`/`inset-e-` and `start-`/`end-` (not `left-`/`right-`),
  `border-s`/`border-e`, `text-start`/`text-end`, `float-start`/
  `float-end`, `ms-auto` (not `ml-auto`). These read as
  `*-inline-start`/`*-inline-end` and flip under RTL. `lint:fix`
  canonicalises them (e.g. `start-2` → `inset-s-2`). Symmetric utilities
  (`px-`, `mx-`, `inset-x-`, `gap-`) need no change.
- **Directional icons flip** with the `rtl:` variant — `rtl:-scale-x-100`
  on the arrow span (the Button `iconRight`, the "+N more" / "read more"
  `→`). Vertical/rotational/diagonal icons (`↑ ↓ ↻ ↗`) and the wordmark
  logo are **not** mirrored.
- **User-content names carry `dir="auto"`** (tile names, signer pills +
  tooltips) so a Latin name in an RTL page — or an Arabic name in an LTR
  page — renders with its own direction.

Known follow-ups (the AC is met; these are refinements):

- **Radix tooltips** still default to LTR alignment (no direction
  context). The language switcher and squad filter popovers are handled
  (DEV-72 flips `Popover.Content`'s `align` to `end` under RTL); the
  remaining tooltip cases are minor and would be covered by a
  `DirectionProvider`. **`@radix-ui/react-direction` is now a direct dep**
  (DEV-44): the player-card modal (`PlayerCardModal`) wraps its tree in
  `<DirectionProvider dir={…}>`, so the caption dropdown / share popover
  DEV-47 adds inside the card inherit RTL alignment for free. The same
  provider could later wrap the app shell to retire the popover `align`
  workarounds.
- **Player-card swipe direction** (Epic 6 / DEV-45) — done. `resolveSwipe`
  in `~/lib/swipe` maps swipe-in-reading-direction to "next": LTR swipe-left
  advances, RTL swipe-right advances. `Player.astro` passes
  `dir={isRtl(locale) ? "rtl" : "ltr"}` to `PlayerSwipe`. The swipe-hint
  arrows flip with `rtl:-scale-x-100`.
- **Flag-swatch gradients** (inline-style, data-driven) are left
  unmirrored — a flag's orientation is fixed.

Tested in `tests/e2e/rtl.spec.ts`: `dir`/`lang` per locale, the header
mirrors right, the drop cap floats right, the letter rail moves to the
left gutter, and axe is clean on every Arabic page.

## Adding a new language

1. Add the code to `LOCALES` in `src/i18n/config.ts` (and to
   `RTL_LOCALES` if it reads right-to-left). `astro.config.mjs` and the
   `[lang]/` routes pick it up automatically.
2. Add the code to `LETTER_LANGS` in `schemas/letter.ts` and create
   `content/letter/{code}.md` (start from `en.md`; the campaign team
   translates it — see `letter-editing.md`).
3. Add a dictionary file under `src/i18n/dictionaries/{code}.json`
   (DEV-70) with every key present (English values or `TODO: translate`
   stubs — the CI guard enforces key parity).
4. Add the native language name to the switcher data (DEV-72).

Nothing else — routing, the switcher, and `localiseUrl` all read from
the locale list.

## Working with translators

Translators edit the JSON dictionaries (`src/i18n/dictionaries/*.json`)
and the letter markdown (`content/letter/*.md`) directly; there is no
translation-management system in scope. To translate a key, replace its
`"TODO: translate"` value with the localised string (keep any `{var}`
placeholders intact). The CI key-parity guard
(`tests/unit/i18n/dictionaries.test.ts`) fails the build if a locale is
missing a key that `en.json` has, so a translation can never be silently
dropped. Until a string is translated, the English fallback renders —
safe, never broken.

Word-document deliveries are extracted to this structure (see
`content/translations/incoming/README.md` for the first batch's
extraction notes and the structural calls made on the letter directives).
